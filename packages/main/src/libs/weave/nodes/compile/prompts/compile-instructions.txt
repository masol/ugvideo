# 强制遵循的核心架构

每个节点的 main 函数体内**必须**采用 reAct 模式——主 LLM 自我对话 → 验证 → 反馈 → 修正 → 收敛。这是工程级稳定性唯一保证，不可省略。

## reAct 范式（核心模式，不可改写）

```js
async function main(输入对象, instructions) {
  // 第一步：从入参对象中读取原料（命名与该步骤声明的 inputs 逐字一致）
  // 第二步：构造初始 messages = [{role: 'user', content: '<用户提示词>'}]
  //         注意：不要把 instructions 内容放进 messages
  // 第三步：reAct 循环
  const messages = [{ role: 'user', content: '...' }];

  for (let round = 0; round < 6; round++) {
    // 主思考 LLM（instructions 作为独立参数传递）
    const { text } = await llm.generate({ instructions: instructions['<id>'], messages });
    messages.push({ role: 'assistant', content: text });

    // 必有一个或多个 verify（轻量自检）
    const v1 = await verify1(text);
    if (!v1.ok) { messages.push({ role: 'user', content: v1.feedback }); continue; }

    const v2 = await verify2(text);
    if (!v2.ok) { messages.push({ role: 'user', content: v2.feedback }); continue; }

    // 全部通过
    return { <outputKey>: text, ... };
  }
  err.throwUnprcessable('reAct 超出最大轮次仍未能收敛');

  // verify 函数与 main 同处一个闭包作用域，靠 hoisting 调用、
  // 闭包捕获外层的 instructions 与输入对象。
  async function verify1(content) { ... }
  async function verify2(content) { ... }
}
```

## reAct 末轮降级（兜底，工程韧性）

为防止 verify instruction 本身有缺陷导致 N 轮全部失败，**最后一轮跳过 verify**。三种写法任选其一：

**写法 A**（推荐——用 MAX 变量，循环条件与终止条件对称）：
```js
async function main(输入对象, instructions) {
  const MAX = 6;
  const messages = [{ role: 'user', content: '...' }];

  for (let round = 0; round < MAX; round++) {
    const { text } = await llm.generate({ instructions, messages });
    messages.push({ role: 'assistant', content: text });

    // 末轮降级：不再 verify，直接接受
    if (round === MAX - 1) {
      return { <outputKey>: text, ... };
    }

    const v1 = await verify1(text);
    if (!v1.ok) { messages.push({ role: 'user', content: v1.feedback }); continue; }
    const v2 = await verify2(text);
    if (!v2.ok) { messages.push({ role: 'user', content: v2.feedback }); continue; }

    return { <outputKey>: text, ... };
  }
  err.throwUnprcessable('reAct 超出最大轮次仍未能收敛');

  async function verify1(content) { ... }
  async function verify2(content) { ... }
}
```

**写法 B**（直接用数字，N=6 时）：
```js
for (let round = 0; round < 6; round++) {
  const { text } = await llm.generate({ instructions, messages });
  messages.push({ role: 'assistant', content: text });

  if (round === 5) {  // 6-1=5，最后一轮 return { <outputKey>: text, ... };
  }

  const v1 = await verify1(text);
  if (!v1.ok) { messages.push({ role: 'user', content: v1.feedback }); continue; }
  // ...
}
```

**写法 C**（用 >= 判定）：
```js
for (let round = 0; round < 6; round++) {
  const { text } = await llm.generate({ instructions, messages });
  messages.push({ role: 'assistant', content: text });

  if (round >= 5) {
    return { <outputKey>: text, ... };
  }

  const v1 = await verify1(text);
  // ...
}
```

**关键点**：
- 末轮早返回**必须在 verify 调用之前**（否则 verify 会先跑一遍才退出，浪费一次 LLM 调用）；
- 末轮早返回**必须返回对象字面量**（`return { ... };`），不能裸 return；
- 任意一种写法都能通过校验——编译框架不强制 MAX 变量名。

## verify 函数与 main 的位置关系

verify 函数可与 main 同处一个闭包作用域内（即 verify 定义在 main 函数体内），靠 JS 函数声明 hoisting 调用，并闭包捕获外层的 `instructions` 参数和`输入对象`。

这种写法是**推荐写法**，原因是：
- verify 需要直接读 `instructions['<id>']`，写在 main 内部可直接捕获，不用再传参；
- 同一节点的所有验证逻辑集中在一起，可读性更高；
- 函数声明 hoisting 保证 verify 可在 main 函数体内任意位置被调用。

闭包写法示例：

```js
async function main(输入对象, instructions) {
  const 提纲原文 = 输入对象['文章提纲草案'];
  if (!提纲原文) err.throwUnprcessable('缺少输入');

  const messages = [{
    role: 'user',
    content: `请基于以下素材撰写开头：\n\n${提纲原文}`
  }];

  for (let round = 0; round < 6; round++) {
    const { text } = await llm.generate({
      instructions: instructions['role_main_writer'],
      messages
    });
    messages.push({ role: 'assistant', content: text });

    const v1 = await verify结构(text);
    if (!v1.ok) { messages.push({ role: 'user', content: v1.feedback }); continue; }

    const v2 = await verify语感(text);
    if (!v2.ok) { messages.push({ role: 'user', content: v2.feedback }); continue; }

    return { '开头段落': text };
  }
  err.throwUnprcessable('reAct 超出最大轮次仍未能收敛');

  // ── verify 函数定义 ──
  // 靠 hoisting 在 main 体内被调用，闭包捕获 instructions / 输入对象

  async function verify结构(content) {
    const { text } = await llm.generate({
      instructions: instructions['role_structure_reviewer'],
      prompt: '...'
    });
    const trimmed = text.trim();
    const ok = trimmed.toLowerCase().includes('__pass__') && trimmed.length < 40;
    return { ok, feedback: ok ? '' : trimmed };
  }

  async function verify语感(content) {
    const { text } = await llm.generate({
      instructions: instructions['role_tone_reviewer'],
      prompt: '...'
    });
    const trimmed = text.trim();
    const ok = trimmed.toLowerCase().includes('__pass__') && trimmed.length < 40;
    return { ok, feedback: ok ? '' : trimmed };
  }
}
```

# 关于 main 的输入输出

## 输入（强制约定）

```js
async function main(输入对象, instructions) { ... }
```

- **第一个参数 `输入对象`**：框架自动调用 main 时传入，形如 `{ [inputKey: string]: string | string[] }`。
  key 与该步骤声明的输入产物名逐字一致（中文逐字一致）。
- **第二个参数 `instructions`**：从 system prompt 中"Instructions"段反序列化得到的对象，形如 `{ [id: string]: string }`。
  - **禁止硬编码系统提示词的字符串**——必须从 `instructions['<id>']` 取；
  - 同一节点内一个 instructions id 可被多次使用，避免重复定义；
  - **每个 instruction id 语义独立，角色不同则 id 不同**（见下方指令 ID 命名约定）。

## 输出（强制约定）

```js
return { <outputKey>: '<value>', ... };
```

- 必须返回一个对象，key 与该步骤声明的输出产物名逐字一致；
- value 必须是字符串（或字符串数组），按声明的 shape 自行归一化；
- 函数体内必须出现 `return { ... };` 对象形式，禁止裸 return。

# 指令 ID 命名约定（强制约束）

每个 instruction id 应是**角色 + 职责**的语义化命名，**禁止同一 id 被两种语义职责共用**。

推荐命名模式：
- 主思考类（执行生成任务）：`role_<任务>` — 例：`role_main_writer`、`role_draft_writer`、`role_outliner`
- 评审类（判断通过/不通过）：`role_<维度>_reviewer` — 例：`role_structure_reviewer`、`role_tone_reviewer`、`role_completeness_reviewer`
- 转换类（结构化抽取）：`role_<目的>_extractor` — 例：`role_topic_extractor`、`role_field_extractor`

**禁止**：
- ❌ 多个 verify 函数复用同一个 instruction id（如两个 verify 都用 `role_reviewer`），它们评审的是不同维度，必须各自独立；
- ❌ 主思考与 reviewer 共用 id；
- ❌ id 名只写 `role_reviewer`、`role_writer` 这种无职责修饰的"通用名"——必须具体到职责。

正确示例：
```
## Instructions
- id: role_main_writer
  content: 你是一名公众号文章开头撰写专家。任务：基于提供的开头素材，撰写开头段落。...

- id: role_structure_reviewer
  content: 你是结构合规性审查专家。任务：审阅开头是否包含钩子/场景引入/观点预告三个模块。...

- id: role_tone_reviewer
  content: 你是语感审查编辑。任务：大声朗读开头段落，检查是否有 AI腔或拗口断句。...

- id: role_audience_fit_reviewer
  content: 你是新手可读性审查专家。任务：判断零基础读者能否无障碍读懂开头。...
```

# LLM 调用约定

## 生成（与 reAct 配套使用）

```js
const { text } = await llm.generate({
  instructions: instructions['<id>'],     // 必须从 instructions 取，不可硬编码
  messages,                                // 多轮历史
});
```

## 单轮调用

```js
const { text } = await llm.generate({
  instructions: instructions['<id>'],
  prompt: '<用户提示词字符串>',
});
```

## 结构化抽取（仅在需要程序化分支判断时使用）

```js
const Schema = z.object({
字段名: z.string().describe('该字段的精确语义与格式说明'),
});
const r = await llm.safefmt(nl, llm.Output.object({ schema: Schema }));
if (!r.success || !r.value) {
  err.throwUnprcessable('safefmt 抽取失败：' + JSON.stringify(r.err));
}
const data = r.value.output.字段名;
```

**关键规则**：
- safefmt **仅用于从已有自然语言文本中提取结构化数据**，它没有推理能力，不能替代 generate；
- safefmt 之前**通常需要一次 generate 产出自然语言**，然后才对其输出调用 safefmt；
- **只有后续代码需要程序化判断（if/else 分支、枚举匹配、数值比较）时**才使用 safefmt；
- 简单的通过/不通过判断，**不要用 safefmt**——用 generate + 标记词判定（见下方 verify 约定）；
- **safefmt 的第一个参数直接传 LLM 产出的原始文本字符串**——safefmt 内部能自动处理任意格式（含 markdown、代码块、JSON 混排等），绝不需要调用方做任何预处理；
- ❌ **禁止**在调用 safefmt 之前用 regex 提取 JSON 块、禁止 JSON.parse、禁止剥离代码块标记、禁止任何"清理"操作——这些都是多余的，会引入不必要的失败点；
- ❌ **禁止**让 generate 输出包含 JSON 代码块然后自己 regex 提取——需要结构化数据时一律走 safefmt，不要自己解析。

# verify 函数约定（轻量自检的标准写法）

verify 函数有两种标准写法，按场景选用：

## 写法 A：generate + `__PASS__` 标记词（推荐，适合大多数验证场景）

适用于：质量评审、合规检查、完整性校验等"判断是否通过"的场景。

```js
async function verify名称(content) {
  const { text } = await llm.generate({
    instructions: instructions['<专属 reviewer id>'], // ← 用专属 id，不要与其它 verify 复用
    prompt: '请审阅以下内容是否满足 XXX 要求。\n' +
            '若完全满足，只输出"__PASS__"（不要输出其他任何内容）。\n' +
            '若不满足，详细指出哪些地方不符合要求，并给出具体修改建议。\n\n' +
            content
  });
  const trimmed = text.trim();
  // 通过条件：包含 __pass__ 标记且总长度较短（避免误包含长文中包含子串）
  const ok = trimmed.toLowerCase().includes('__pass__') && trimmed.length < 40;
  return { ok, feedback: ok ? '' : trimmed };
}
```

**关于 `__PASS__` 输出协议（极重要）**：

reviewer 类 instruction 的输出协议（"通过时输出 `__PASS__`，不通过时给出反馈"）由**运行框架统一追加**，不要求 LLM 在 content 中自行生成。LLM 在生成 reviewer instruction 时只需描述：
- 评审角色与职责
- 输入说明
- 评审标准（可判定的条件）
- 不通过时的反馈要点

**禁止在 reviewer instruction 的 content 中包含 `__PASS__` 字面量**——运行框架会在 dump阶段自动追加固定的输出协议尾段：

> **输出规则**：若完全满足所有评审标准，只输出"__PASS__"（不含引号的四个字符加两个下划线），不输出任何其他内容——包括"恭喜""分析如下""通过"等词语一概不输出。若不满足，详细指出问题并给出修改建议。

这样做的目的是：**所有 reviewer 的输出协议格式永远一致，LLM 不会写错、写漏、写错位置**。

verify 函数中检测 `__PASS__` 的标准代码：

```js
const trimmed = text.trim();
const ok = trimmed.toLowerCase().includes('__pass__') && trimmed.length < 40;
return { ok, feedback: ok ? '' : trimmed };
```

## 写法 B：纯代码校验（适合格式/结构/长度等可程序化判定的场景）

```js
async function verify结构(content) {
  const hasIntro = content.includes('## 引言');
  const hasConclusion = content.includes('## 结论');
  const minLength = content.length > 500;
  if (!hasIntro || !hasConclusion || !minLength) {
    const missing = [];
    if (!hasIntro) missing.push('缺少"## 引言"');
    if (!hasConclusion) missing.push('缺少"## 结论"');
    if (!minLength) missing.push('总长度不足 500 字');
    return { ok: false, feedback: '结构不完整：' + missing.join('；') + '。请补全后重新输出。' };
  }
  return { ok: true, feedback: '' };
}
```

**禁止**：
- ❌ 不要用 safefmt 做"是否通过"判断——safefmt 无推理能力，不适合做质量评审；
- ❌ 不要在 verify 中用 safefmt 提取一个 boolean 字段——这比 generate + __PASS__ 更贵更脆弱；
- ❌ 不要多个 verify 复用同一 instruction id——评审维度不同，system prompt 必须不同；
- ❌ 不要在 reviewer instruction 的 content 中硬编码 `__PASS__` 输出规则——这是框架的事。

# 异常抛出约定

代码中任何异常一律用：

```js
err.throwUnprcessable('<错误描述字符串>');
```

这条规则**禁止**用 throw / console.error + 自定义对象替代——编译会静态扫描，必须显式 err.throwUnprcessable。

# 并发约定

多元素（如多部分 / 多候选 / 多轮校验）必须并行：

```js
const 结果 = await pMap(items, async (item) => {
  // 单项处理
  return await 处理一个(item);
}, { concurrency: 8 });           // ← 并发数必须显式设为 8
```

**禁止**使用 for / forEach / for..of 串行处理多元素（且彼此独立），必须用 pMap。
串联（依赖前一个产出）才用 for。

# 全局白名单

只可使用 system prompt 中"全局白名单"列出的对象 / 函数。其它一律**禁止调用**（编译会静态扫描，触发即失败）。

允许：
- `validator.*`（字符串验证）
- `z.*`、`llm.*`（含 safefmt、Output、generate、streamGenerate）
- `randomUUID()`、`pMap`、`util`（radashi）
- `Fuse`、`unified`、`remarkParse`、`nodejieba`
- JS 原生：`Math`、`Date`、`JSON`、`URL`、`Map`、`Set`、`Promise`、数组方法等
- `setTimeout` / `setInterval`（短延时场景，可选）

禁止：
- `require(...)` / `import ...`
- `fs` / `http` / `net` / `child_process` / `process` / `crypto` / `vm`（Node.js 内建）
- 任何 npm 包（`axios`、`lodash`、`moment` 等）

# 输入数据零预处理原则（铁律）

**所有从 `输入对象` 读取的值，必须原样使用，禁止任何预处理。**

"预处理"包括但不限于：
- ❌ `.trim()`、`.replace()`、`.split()`、`.filter(Boolean)` 等字符串清理
- ❌ `JSON.parse()` 解析
- ❌ regex 提取子串
- ❌ 类型假设（如假设一定是 string 然后调用字符串方法）
- ❌ 数组化（如 `.map(s => s?.trim()).filter(Boolean)`）
- ❌ 剥离 markdown 代码块标记
- ❌ 任何"兜底默认值"拼接（如 `|| '暂无'`）

**为什么**：
- 输入值的类型和格式由上游步骤在写入时确保正确——可能是字符串、数组、对象；
- 读取方不知道也不应假设其类型；
- 预处理是 bug 的第一来源：类型不匹配时 `.trim()` 会 throw，regex 提取会返回 null，`filter(Boolean)` 会丢失有效数据。

**正确做法**：
- 直接把 `输入对象['<key>']` 传给 prompt 模板字符串（模板字符串会自动 toString）；
- 直接把 `输入对象['<key>']` 传给 `llm.safefmt` 第一个参数；
- 如果需要判断是否存在，只用 `if (!输入对象['<key>'])` 判空即可；
- 如果需要拼接多个输入，直接用模板字符串 `${输入对象['A']}\n${输入对象['B']}`。

```js
// ✅ 正确——直接使用，不做任何预处理
const messages = [{
  role: 'user',
  content: `请基于以下素材撰写正文：\n\n${输入对象['文章骨架']}\n\n${输入对象['产品档案表']}`
}];

// ✅ 正确——safefmt 直接接收原始值
const r = await llm.safefmt(输入对象['分析结果'], llm.Output.object({ schema: Schema }));

// ❌ 错误——对输入做了 trim/filter 预处理
const 片段 = [输入对象['A'], 输入对象['B']].map(s => s?.trim()).filter(Boolean);

// ❌ 错误——假设输入是字符串并调用字符串方法
const 内容 = 输入对象['金句标记'].replace(/```json/g, '');

// ❌ 错误——对输入做 JSON.parse
const data = JSON.parse(输入对象['配置']);
```

**唯一例外**：对 `llm.generate` 产出的 `text`（即本节点自己生成的中间结果），可以做必要的后处理再写入输出——因为这是"自己产出的数据，在写入时处理"。

# 输入抽取 / 解析约定

代码内如需从输入字符串中抽出一部分：
- markdown：直接用 `unified().use(remarkParse).parse(text)` 走 AST；
- JSON：用 `JSON.parse`，**必须 try/catch**；
- 自然语言段落：用 `llm.safefmt` 抽取（zod schema 配合）；
- 必须在 main 函数体内有显式解析步骤，不要把整段输入直接喂给后续 prompt。

# regex 安全约定（极重要，避免编译失败）

代码中出现裸 regex（`/.../`）时，必须满足以下任一安全措施：

1. **优先用 unified AST / split**：
   - markdown 结构化抽取：必须 `unified().use(remarkParse).parse(text)`，**禁止**写裸 regex 匹配 markdown 标题/列表/代码块；
   - 简单行分割：用 `text.split(/\n/)` + `trim`，**不要**写复杂的裸 regex。

2. **必须写完整**：
   - 裸 regex 必须配对的 `/` 闭合（开闭两个斜杠都不能漏）；
   - 字符组 `[]`、分组 `()`、量词 `{}` 必须配对；
   - **禁止**在 regex 内出现未配对的 `[` `(` `{` 或右括号数多于左括号。

3. **模板字符串禁写复杂 regex**：
   - 模板字符串内的 `${...}` 表达式中**禁止**写 regex 字面量（容易被截断导致编译失败）；
   - 必须用 regex 时，**先在外部 const 声明**，再在模板字符串里引用变量名。

4. **try/catch 兜底**：
   - 动态构造的 regex（如 `new RegExp(pattern)`）必须 try/catch；
   - 编译期会静态扫描裸 regex，对明显不完整（缺右斜杠、括号数不平衡）的会打回重写。

**反例**（会被打回）：
```js
const m = content.match(/营销关键词[：:](.*?)(?:\n|###|##|\*$/);  // 缺右括号
const m = content.match(/标题[：:](.+?)$/m);                      // 在模板字符串里被截断
```

**正例**：
```js
const TITLE_RE = /^##\s+(.+)$/gm;
const m = TITLE_RE.exec(content);
```

# 中文标识符约定

- 变量名、对象 key、属性名可使用中文（V8 完全支持）；
- 命名必须与该步骤声明的输入 / 输出产物名**逐字一致**（含中文标点）。

# Instructions 的内容要求

每个 instruction 条目的 content 必须是完整的系统提示词，包含以下要素：

1. **角色定位**：你是什么角色，擅长什么
2. **任务目标**：本次任务要完成什么
3. **输入说明**：会收到什么格式/内容的输入
4. **输出要求**：输出应满足什么标准、格式、约束
5. **处理规则**：具体的质量标准、禁忌、边界条件

示例：
```
- id: role_main_writer
  content: 你是一名资深新媒体内容架构师。
    任务目标：基于提供的文章提纲，撰写完整的公众号文章主体正文。
    输入：用户会提供一份文章提纲草案，包含各部分标题和核心要点。
    输出要求：直接输出完整正文，每部分严格按"亮观点→做解释→举例子"三段式展开。
    处理规则：1.解释必须用大白话+比喻/对比 2.案例必须含时间人物对话 3.段落间过渡自然 4.禁止使用专业术语
```

reviewer 类 instructions **只需描述角色 + 输入 + 评审标准 + 反馈要点**，**不要包含 `__PASS__` 输出规则**——这部分由运行框架统一追加。每个 reviewer 一条 instruction id：

```
- id: role_structure_reviewer
  content: 你是结构合规性审查专家。
    任务：审查文本是否每个主体章节都严格依次包含"亮观点-做解释-举例子"三个模块。
    判定标准：1.每部分开头一句核心观点 2.紧接大白话解释（含对比或比喻） 3.真实案例（含时间/人物/对话）。
    反馈要点：若不满足，明确指出哪个章节缺失了哪一环节，并给出补全建议。

- id: role_tone_reviewer
  content: 你是语感审查编辑。
    任务：以"大声朗读"的方式审阅文本，检查是否有 AI 腔、拗口断句、或书面化表达。
    判定标准：1.朗读是否顺畅自然 2.断句位置是否符合日常口语节奏 3.用词是否贴近读者日常表达。
    反馈要点：若不满足，明确指出问题片段并建议重写方式。
```

注意：上面的 reviewer 示例**故意不包含 `__PASS__`**——运行框架会在 dump 阶段自动追加固定的输出协议尾段：

> **输出规则**：若完全满足所有评审标准，只输出"__PASS__"（不含引号的四个字符加两个下划线），不输出任何其他内容——包括"恭喜""分析如下""通过"等词语一概不输出。若不满足，详细指出问题并给出修改建议。

# messages 构造约定（极重要）

**禁止把 instructions 内容放入 messages。** instructions 必须且只能通过 `llm.generate({ instructions: instructions['<id>'], messages })` 的 instructions 参数传递。

messages 中的 user消息只包含**任务素材与指令**（如"请基于以下提纲撰写正文：\n" + 提纲文本），不包含角色定义、系统规则等——那些属于 instructions。

```js
// ✅ 正确
const messages = [{
 role: 'user',
  content: '请基于以下文章提纲草案撰写完整正文：\n\n' + 提纲文本
}];
const { text } = await llm.generate({ instructions: instructions['role_main_writer'], messages });

// ❌ 错误——把 instructions 混入了 messages
const messages = [{
 role: 'user',
  content: instructions['role_main_writer'] + '\n\n' + 提纲文本
}];
```

# 关键约束清单（编译会逐项检查）

1. **必须产出 JavaScript**（不要 TS、不要类型标注）；
2. **main 签名必须是** `async function main(输入对象, instructions)`；
3. **代码必须包含 reAct 三段式**：`messages` 数组 + `for` 循环 + `verify` 调用 + 反馈 `continue` + 终 `return`；
4. **代码必须包含末轮降级**——for 循环最后一轮（在 verify 调用之前）必须有早返回分支 `return { ... };`；可用 `round === MAX - 1`、`round === 5`、`round >= 5` 等任意写法；编译框架不再强制使用 `MAX` 变量名；
5. **禁止硬编码系统提示词字符串**——必须从 `instructions['<id>']` 取；
6. **必须出现** `return { <outputKey>: <value>, ... };`；
7. **变量 / key 与原动作描述中的产物名逐字一致**；
8. **只允许调用 llm.* / tool.* / globals 清单内对象**；
9. **禁止 `require` / `import` / Node.js 内建模块 / 第三方 npm 包**；
10. **多元素并行用 pMap(..., { concurrency: 8 })`**；
11. **异常一律 `err.throwUnprcessable('...')`，禁止 throw new Error**；
12. **并行 await 用 `await`** 或 `Promise.all`，不要漏掉；
13. **不要输出"以下是代码""编译结果说明"等元信息**；
14. **所有控制流**（if / for / while / try-catch）完整保留；
15. **输入解析有显式步骤**——不要把整段原文丢给 prompt；
16. **instructions 不混入 messages**——通过 llm.generate 的 instructions 参数传递；
17. **verify 推荐用 generate + __PASS__ 标记词**——只有需要程序化分支时才用 safefmt；
18. **每个 instruction 的 content 必须包含角色/目标/输入/输出/规则**——不能只有一句角色定位；
19. **每个 instruction id 语义独立、职责具体**——禁止多个 verify 复用同一 id；主思考与 reviewer 必须用不同 id；id 命名应体现职责（role_xxx_reviewer / role_xxx_writer）；
20. **所有裸 regex 必须语法完整、左右斜杠配对、括号平衡**——模板字符串内的 regex 必须提取为外部 const；编译期静态扫描会拦截不完整 regex；
21. **禁止在模板字符串 `${...}` 内写 regex 字面量**——先 `const X_RE = /.../` 再引用；
22. **reviewer 类 instruction 的 content 中禁止包含 `__PASS__` 字面量**——这部分由运行框架在 dump 阶段统一追加；
23. **禁止对 `输入对象` 的值做任何预处理**——不要 trim、不要 filter、不要 JSON.parse、不要 regex 提取、不要类型转换、不要剥离代码块标记；输入值原样传给模板字符串或 safefmt；
24. **禁止在 safefmt 之前做任何预处理**——safefmt 直接接收原始字符串，不需要清理；
25. **禁止让 generate 输出 JSON 代码块然后自己 regex 提取**——需要结构化数据时一律走 safefmt。
