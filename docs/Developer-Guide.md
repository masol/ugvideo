# 📐 工作流开发总览（开发者指南）

本页面向**构建**工作流的开发者，是所有开发者文档的入口和地图。

> **版本提示（0.0.3-pre-alpha）**：当前开发者能真正上手的是 `/plan` 规划能力（从一句话生成可执行的多层 DAG）与 `/prism` 推理。蓝图编辑、`/export` 发布等链路仍在打磨中，本页部分内容描述的是**目标形态**。

## 心智模型：你在开发什么

在 Unigen 中，工作流以**代码**形式存在（在界面中称为**蓝图**），可动态加载。选择代码而非配置 DSL，是一个刻意的决定：**为了让规划器（而不只是人）能够修改它**——规划器正是通过修改蓝图内容来改进工作流的。

需要先厘清一件事：Unigen 里运行的是**预定义工作流**（Predefined Workflow），不是边想边做的自主代理（Agentic System）。它和 Coze、Dify、n8n 同属一类，区别在于——**工作流本身也由 AI 创建并持续更新，且这一过程受逻辑体系约束，以“无幻觉、不漂移”为最高目标**（详见 [[欢迎首页|Home]] 的定位说明）。

"开发工作流"这件事本身也是一个工作流，因此它也是一种项目类型——当前版本中，**工作流工坊**（用来开发工作流、并导出为新项目类型的项目）即内建了这个能力（当前主要通过 `/plan` 规划落地）。

正因为"节点是被规划器长出来的"，Unigen 与 LangChain / Mistral 这类现成工作流框架处在不同的坐标系里——下一节说明为什么不能直接用它们。

## 为什么不用 LangChain / Mistral 这类现成工作流

它们是优秀的工程，但优化的是**另一个问题**。三处根本前提不同，使它们不适配 Unigen：

**1. 节点是"人写的稳定组件" vs "机器长出的临时叶子"。**
LangChain / Mistral 的节点由**人**编写、复用、长期维护，框架的价值在于让人搭图更快、更好维护。Unigen 反过来：节点代码由 **LLM 在独立上下文中，依据该节点与其所属维度动态生成、动态修改**，规模都很小、受 node kind 约束、**默认不由人维护**。我们要优化的不是"人写图的表达力"，而是"机器长图的可生成性与可校验性"——结构合法性由代码骨架硬保证，语义由 LLM 局部填充。目标函数不同，工具自然不同。

**2. 代码是"骨架"而非"内容"。**
在 Unigen 里，工作流的主体信息不在代码里，而在**维度**里；代码只是每个维度末端一段短小的、配套的叶子实现。现成框架假设节点内含实质业务逻辑、值得被抽象和复用；而 Unigen 的节点是"够用即弃"的产物，抽象与复用的收益转移到了维度层，不在代码层。

**3. 节点间通信是 NL 字符串，而非静态 JSON。**
现成框架在节点间传结构化数据（JSON / 类型化对象），前提是 **schema 预先约定**。但 Unigen 的节点是被规划器**动态长出来的**——你无法为尚不存在的未来节点预定义一个覆盖全部情况的静态 schema。因此节点间默认传**自然语言字符串**：把 NL 看作一份"携带语义的 JSON"，只不过它的解码器是 LLM 而非 `JSON.parse`。

这需要讲清楚一个必然被追问的点——**既然更贵、更慢、还不完全可靠，为什么不干脆用 JSON？** 因为二者承担**同一角色（结构化载荷的搬运），但适配的前提根本不同**：JSON 是**封闭 schema** 下的无损搬运，NL 是 **schema 尚未存在**时唯一仍能携带完整语义的载体。贵与慢，是为"结构未被预先约定"支付的必要代价，不是缺陷——它恰恰是"代码作骨、LLM 填充"在通信层的体现。现成框架为封闭 schema 而生，天然无法承接这一前提。

> 一句话：LangChain / Mistral 优化"人搭稳定的图"，Unigen 优化"机器长临时的图并保证它不崩"。前者的最佳实践（复用节点、静态类型通信）恰是后者的约束。用它们的直觉读 Unigen，会处处别扭。

## 当前上手路径：用 `/plan` 规划一条可执行链条

这是当前最实用的开发入口：

1. 新建工作流工坊项目 → 右侧面板 → 反思助手。
2. `/plan --no-codegen=on --cap=new "你的目标（如：从剧本到视频）"` 得到多层 DAG。
3. 「蓝图 → 术语表」用 `.` 过滤 → Action Button → 面板显示，查看 DAG。
4. DAG 工具栏录入原始数据 → 执行；缺代码的节点用 `/plan --cap=节点ID` 补齐。
5. 查看/编辑节点的代码与元信息，人工介入打磨质量。

> 当前规划只做可行性校验（无环、依赖闭合），质量维度需要人工在生成的代码上介入改进——这也是 [[路线图|Roadmap]] 中"自我改进不动点"要逐步接管的部分。详见 [[逻辑向AI：维度、坐标系与两种逼近|Logic-Oriented-AI]]。

## 两个核心工作面

打开项目后，你主要在两个地方工作：

### 反思助手（右侧面板，须有项目打开）

命令式交互入口，可执行 `/plan`、`/prism` 等命令、发布任务。建议配置 OpenTelemetry 接收器（如 Phoenix）以拿到全量日志。

### 蓝图（工作流细节）

点击**蓝图**可查看和编辑工作流的全部细节。注意两点：

1. 你的手工编辑和规划器的自动改进作用在**同一份蓝图**上——这是"人工可介入 + AI 可持续改进"得以共存的载体。
2. 蓝图的用户配置界面由一棵 JSON 描述，见 [[动态面板 JSON 指南|Panel-JSON]]。

## 开发到发布的路径（目标形态）

```
工作流工坊 → /plan 规划出可执行 DAG → 蓝图中打磨工作流 → 实际运行验证 → /export 导出为项目类型 → 发布给创作者
```

> 其中蓝图深度编辑与 `/export` 发布仍在打磨中；当前可稳定完成的是"规划 → 生成代码 → 录入数据 → 执行"这段。

## 姿势二：规划器生成（演进中）

Unigen 的终极目标是让工作流的产生、改进、维护都由规划器接手。规划器路线分三阶段推进（Prism → Loom → HTN），参考其它文档。当前已落地约 1% 的 Loom（只做可行性校验），质量/成本/效率维度与自我改进不动点见 [[路线图|Roadmap]]。

三层共同的立场：**代码作骨、LLM 填充**——结构合法性（无环、依赖闭合、词表统一）由代码硬保证，LLM 只负责局部语义。这是对"长链条漂移零容忍"的落实。

## 架构速览

- **执行器**：调度与运行原子动作，捕获环境反馈，负责生产容错。
- **规划器**：把高层意图编译成结构合法的任务路径，通过修改蓝图落地。不干活，只编译。
- **执行历史**：OpenTelemetry 兼容采集，一切改进以真实运行记录为依据。
