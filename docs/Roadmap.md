# 🧭 路线图

Unigen 的推进顺序：**先兑现确定性的用途,再逐步交给规划器。**

## 当前实况（0.0.3-pre-alpha）

- **已实现**：最小化 Loom 规划（约 1%）——从一句话规划出多层 DAG、为节点生成代码、录入数据后可执行；`/prism` 推理可直接体验。
- **规划当前只做可行性校验**（无环、依赖闭合），尚未实现：质量维度拆分、质量校验、成本平衡、效率优化。所有类别套同一套生成策略。
- **尚无任何成熟可交付的工作流。**

接下来的两条主线是：**(A) 补齐规划的质量维度、搭建归约器动态生长的基础**，与 **(B) 用现有方法人工构建高质量工作流**。两者并非互斥（见文末「下一步」）。

## 历史项目背景

本路线背后是多年对**任意长链条、强一致性人工工作流**的实证探索。已验证可行性（但都是手工搭建、试验导向）的项目包括：小说→视频（逻辑稳定、无长度限制）、自动撰写30万字小说并发番茄测试、产品需求→微信公众号长文等。这些试验为本路线提供了：
- **真实失败案例库**：哪些类型的归约约束是手工项目里反复出问题的。
- **长链条可行性背书**：用逻辑骨架接管长链条任务是可做到的（人已经手工做到了，自动化只是工程问题）。
- **质量维度样本**：哪些维度（如人物一致性、情节连贯、风格统一）在长链条里是真正承重的。

部分历史产物可在 https://lizt.top 体验。这些经验催生了当前的**可自我改进的通用规划器**。


## 第一步：承载有实际意义的工作流

优先落地一批真实价值的长链条工作流：

- 剧本 → 视频
- 创意/要求 → 小说
- 小说 → 剧本
- 需求 → 代码（可能聚焦细分类目，如 Web）

这一阶段以人工撰写为主、内建方法（Plan 等）辅助，同时验证平台本身：稳定 / 高效 / 灵活的运行，以及工作流发布能力。

## 第二步：规划器接手生成与改进

按 [[Prism（视角层）|prism]] → Loom（结构层过渡）|loom → HTN/HDDL（结构层完全体）|planner 推进，让工作流的产生、改进、维护尽可能由规划器完成。基于 OpenTelemetry 执行历史的持续改进也在这一阶段落地。

## 终极目标

**无人介入，全自动改进。** 更远处是认知模型 / 世界约束层（见 [[棱镜推理|prism]] 第九节）——让规划器知道"什么客观上做不到"，目前是开放研究。

需要说明：本路线所说的"自我改进"有严格的数学天花板，它不是"无限超越"，而是"在给定逻辑框架与环境约束下收敛到极限"。从收敛极限到真正的"自我进化"（主动改造环境、跳出自身框架），中间隔着一道从工具到生命的鸿沟。这条边界的详细分析见 [[自改进的边界|self-improvement-boundary]]。

## 说给使用者：Plan 能做什么、极限在哪

抛开数学，用大白话说清 `/plan` 这条路的用途与边界，避免过度期待：

- **想做成的事（愿景）**：你提出需求，系统生成一条能跑出成品的工作流。理论射程覆盖**人类已经反复解决过的工程类长链任务**——写小说、剪视频、按需求出代码这类"有人做成过、只是又长又累"的活。这类任务"好办法存在"是有保证的（人做到过），问题只在能否被自动找到。
- **现在的现实**：0.0.3 版质量粗糙、又慢又费 token，上面这个愿景**远未兑现**。所以现阶段请把 `/plan` 当作"体验这条路的感觉"，而不是"能替你干活的工具"。
- **就算兑现了，也到不了的地方**：**范式创新**——像图灵发明计算模型那样，凭空造出一套前所未有的新认知框架。这类工作要创造的是训练数据里根本不存在的新概念，正落在 LLM 能力的失效区（详见 [[逻辑向 AI|Logic-Oriented-AI]] 第三节）。加上搜索代价极高且没有好的起点，"LLM + 逻辑能否胜任范式创新"是一个**缺乏乐观理由的开放问题**，本路线不承诺、也不以此为目标。

一句话：**目标是稳定接管"又长又难但人类已知怎么做"的工作，不是替代"发明新范式"的工作。** 详细的分层边界见 [[自改进的边界|self-improvement-boundary]]。

## 最想要的社区反馈

- 用**复杂真实任务**验证或证伪 Prism 的"拉平"现象（[[棱镜推理|prism]] 第三、六节）；
- 用 `/plan` 规划复杂任务并回报效果、成本与反例；
- 可量化指标下的严格评测数据；
- Prism / Plan 明显无效或变差的任务类型——反例同样宝贵。

## 自我改进的路径：归约器的动态生长

当前 `/plan` 的核心是**双层 reAct DAG 设计器 + 逻辑展开**（见 `steps/dag.ts` + `steps/p2-expand.ts`）。它能从一句话生成可执行的多层 DAG，但**所有节点套同一套生成策略**，且只有一个手写的归约器（`validateNodes`）拦结构错误。

终极目标要求规划器能**持续改进**——从历史反馈中学习、逐步收紧约束、拦住越来越多的低质量生成。这条路的核心机制不是"规划器替换规划器"（元循环），而是**归约器（validator / checker）的动态生长**。

### 什么是归约器

归约器是**对 LLM 生成结果施加约束的检查器**。它读入一个 DAG（或 DAG 的一部分）、输出"通过 / 不通过 + 原因"。当前代码里已有的归约器雏形：
- `validateNodes`：检查 DAG 结构合法性（无环、依赖闭合、产出唯一、边界对齐）。
- `hooks.review`：在 `designDag` 里可注入自定义评审逻辑（已预留，少量手写实现）。
- `detectEnumByLLM`：检测"未识别的 map 语义"（手动枚举问题）。
- `hooks.postCheck`：在注册层之前最后一道门槛。

这些都是**归约器**——它们把 LLM 的生成空间**归约到满足某个维度约束的子集**。但当前它们都是**手写的、硬编码的**，数量有限（主要就 1 个结构校验器 + 若干钩子）。

### 归约器的动态生长（自我改进的真实含义）

"自我改进"在本项目中的含义是：**归约器集合本身可变**——新归约器从历史反馈中**自动长出来**、旧归约器被禁用或改进、归约器之间的关系（启用条件、互斥、优先级）由逻辑推理动态组合。

具体流程：
1. **反馈采集**：规划结果 + 执行结果 + 最终成品 + 用户反馈（自然语言描述"哪里不对"）→ OpenTelemetry 全量可回溯。
2. **归约器生成管道**（待实现，这是 W1~W6 的核心）：
   - 输入：历史失败案例（DAG + 反馈）。
   - LLM 在独立上下文中生成一个新的归约器（代码 + 逻辑规则），它能拦住这类问题。
   - 沙箱编译校验 + 在若干历史案例上回测 → 通过才被采纳。
3. **归约器的选择与组合**（HTN / HDDL 层，见 [[planner]]）：
   - 给定一个新项目，Prolog 推理引擎根据：
     * 项目分类（小说 / 视频 / 代码 / ...）
     * 归约器之间的逻辑关系（某些互斥、某些是另一些的前提）
   - 输出：本项目启用哪些归约器、以什么顺序调用。
   - 这一步是**维度的演算**（合一 + 回溯 + 谓词折叠），不是简单的"全部启用"。
4. **归约器的迭代**（待实现）：
   - 每个归约器跑完后打分（通过率 / 置信度）。
   - 分数低于阈值时触发"归约器本身的改进"——用反馈重新生成归约器的一个变体。
   - 注：这是"归约器的归约器"（套娃），可能暂不急于实现这一层。

### 与 Prism / Loom / HTN 的关系

- **Prism**：多视角评价的原子操作。归约器本质是"在某个维度（视角）下判断 DAG 是否合格"——一个归约器 = 一个视角。Prism 的"跨视角合并求精"对应归约器的联合约束求解。
- **Loom**：当前阶段。已实现 DAG 生成、逻辑展开、代码生成，但归约器集合是硬编码的。Loom 的任务是**为 HTN 沉淀图数据与实测反馈**，包括归约器的执行历史。
- **HTN / HDDL**：归约器的选择与组合层。维度之间的依赖 / 互斥 / 优先级用 Horn 子句编码，合一算法输出一个可行的归约器启用子集。这是**维度演算的逻辑引擎**。

| - | ------ | -------- | ------------ |

### 系统定位：约束生长机或约束网络（Validator Network）---（待命名）

这套"LLM 生成归约器 + 沙箱回测 + Prolog 组合"的机制，具备**学习机器的核心特征**——从反馈中沉淀约束、约束逐步收紧、行为逐步收敛于"正确"。但它学的不是参数（权重），而是**可枚举的逻辑约束**——这与传统 ML 的学习形态根本不同。

一个**暂用的概念锚点**叫它"**约束生长机**"（待精准命名）：一个由 LLM 充当肉体与感官、由逻辑约束充当骨骼的复合系统，约束从反馈中逐步生长、组合、衰减。这不是"训练-推理"二元结构，没有 loss function 收敛——而是一个**约束网络的渐进式硬化** -- 但它与 ML 学习机器并不相同——独立起名，是避免与 ML 既定定义产生歧义。

### 下一步：尚未决定

这是一个个人项目，背后是多年的研究与大量代码和实验。当整条线在我脑中未自洽时，我原以为剩下的只是"认知问题"——想清楚就能推下去。但当路线逐步清晰之后才明白：拦路的不只是认知，还有一份不成比例的工程量（W1~W6 无一完成），远非一人短期可及。而且清晰本身也带来了新的犹豫：即使走到归约器动态生长，它也只是当前框架的天花板——从天花板到真正的"自我进化"（主动改造环境、跳出自身逻辑框架），中间那道鸿沟我还没有答案。

与之对照的另一条路却低得多、也确定得多：任意长的**人工工作流**，我做过很多、也熟悉它的手感——它简单、当下就有价值，而且每做一个，都会顺带产出 W1/W2 最缺的东西（真实的失败案例与反馈样本）。所以两条路并不互斥：人工工作流是目前**唯一能兑现价值**的产出，同时又是归约器生长的**数据源与校验靶**；反过来，纯埋头改 Plan 而无真实任务反馈，容易在坏坐标系上"严密地跑偏"（见 [[逻辑向 AI|Logic-Oriented-AI]] 第四节）。

按最佳路线，应先补 **W1（归约器元数据表）与 W2（归约器生成管道）**——它们是动态生长的共同前置。但要不要就此把重心从"搭基础设施"移向"多造几个人工工作流"，我还没拿定主意。这一栏会随实际投入更新。

## 为什么反复纠缠 Prism 这个"小技巧"

因为 Prism 不是提质技巧，而是整个系统的最小逻辑单元。它做的事——把一个问题拆成若干正交视角、在每个视角内独立判断、再跨视角合并——正是人类逻辑推理的原子操作：**视角就是维度，而维度是逻辑演算的基础**。人类专家面对复杂问题时并不"更用力地想"，而是不断变换审视问题的维度，直到问题在某组维度下变得显然。

这背后是两条逼近答案的路线：神经网络**固定坐标系**，靠梯度下降拟合一个复合函数；逻辑推理**固定函数、变换坐标系**——不断更换维度（换基底），直到问题在合适的坐标下可解。两者殊途同归（猜想其表达能力等价，此为开放假设，见 [[棱镜推理|prism]] 第四节），但过程与原理完全不同。Unigen 试图把这两条路线接起来：神经元负责在维度内生成，逻辑负责维度的选取、变换与组合——可称之为**逻辑向 AI**。

以此观之，当前 Prism 只是维度演算的**最退化形式**：抽取维度、逐维评价、合并求精。真正的逻辑推理发生在**维度之间**——维度的组合、变换、约束传播——这正是 Loom 与 HTN 阶段要逐级落地的东西，也是这条路若走通、可能触发新范式的原因。地基的每一块砖都要敲实，所以对 Prism 的多视角实测反馈，是当前最迫切需要的。

Prism 背后蕴含的其实是人类的逻辑能力（逻辑拆分再组合的过程），视角是维度，维度之间的演算就是逻辑。因此，Unigen 也可以称为逻辑向 AI——它试图把基于 Horn 范式的逻辑推理与基于神经元的生成式 AI 衔接起来，以实现**超长链条、超高确定性的自我改进**（在逻辑框架允许的范围内）。因此，对于 Prism 的多视角评估，是最迫切需要的。
