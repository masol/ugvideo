# 自改进的边界：从收敛到进化，中间隔着什么

当前路径: wiki/self-improvement-boundary.md

状态: 开放假设与边界标注。本页不是工程文档，而是对 [[路线图|Roadmap]] 中"自我改进路径"的**逻辑边界**做一次标注——它能到哪、不能到哪、以及从"到哪"到"真正的进化"之间，隔的是什么。

---

## 一、三个层级，三个天花板

Unigen 的自我改进路线会依次触碰三个天花板。

```
               ┌──────────────────────────────────────────────┐
               │  L3: 自我进化（待精准命名）                  │
               │  天花板: 未知（开放问题）                    │
               │  突破条件: 主动改造环境 + 跳出自身框架       │
               └──────────────────────────────────────────────┘
                             ▲
                             │ 从工具到生命的鸿沟
                             │
               ┌──────────────────────────────────────────────┐
               │  L2: 归约器动态生长 + 环境自适应             │
               │  天花板: 收敛到当前归约器集合约束的极限      │
               │  突破条件: 归约器生成管道 + Prolog 组合      │
               └──────────────────────────────────────────────┘
                             ▲
                             │ 归约器从硬编码到动态生长
                             │
               ┌──────────────────────────────────────────────┐
               │  L1: 单一归约器 + 手写约束                   │
               │  天花板: 只能拦结构错误,无法拦质量/语义问题  │
               │  Unigen 起点: validateNodes（已实现）        │
               └──────────────────────────────────────────────┘
```

| 层级 | 名称 | 含义 | 天花板（方向性直觉） | 突破条件 |
| ---- | ---- | ---- | -------------------- | -------- |
| L1 | 单一归约器 | 规划器 + 一个手写的结构校验器（`validateNodes`） | 只能拦明显的结构错误（无环、依赖闭合），无法拦质量 / 语义问题 | 引入多个归约器 + 动态生成机制 |
| L2 | 归约器动态生长 + 环境自适应 | 归约器集合可变：从历史反馈中长出新归约器、旧归约器被禁用或改进、归约器之间的关系由 Prolog 推理动态组合 | 收敛到当前归约器集合约束的极限（在当前逻辑框架下的局部最优） | 主动改造环境 + 跳出自身逻辑框架（待精准定义） |
| L3 | 跳出当前框架 | 主动改造环境、跳出自身逻辑框架、产生"后代"并淘汰低效版本 | 未知（开放问题） | 当前不知道 |

**Unigen 当前的工程目标是 L2**：从 L1 起步——`validateNodes` 已实现——逐步搭建归约器动态生长的基础（生成管道、回测、Prolog 组合）。L3 作为**远景方向**列出，但需要说明：从 L2 到 L3，隔的不是工程量，而是**范式跃迁**——本路线目前没有定义清楚"跳出自身框架"具体意味着什么。

## 二、L1 的现状与天花板

当前代码里的归约器集合：
- `validateNodes`（手写，单一）：DAG 结构合法性校验。
- `hooks.review` / `hooks.postCheck`（钩子，少量手写实现）：在 `designDag` 里可注入自定义评审逻辑。
- `detectEnumByLLM`（LLM 调用）：检测"未识别的 map 语义"。
- `p2-expand.ts` 里的 `judgeNode`（LLM 调用）：判定节点是否值得展开。

这些都是归约器的雏形——把 LLM 的生成空间归约到满足某个维度约束的子集。但当前它们都是**手写的、硬编码的**，数量有限，且彼此之间的组合关系没有显式建模（哪些互斥、哪些是另一些的前置）——也就是说，**维度之间的演算**还没有发生。

**L1 的天花板**：只能拦明显的结构错误（无环、依赖闭合），无法拦质量、语义、风格层面的问题。

## 三、L2 的核心机制：归约器动态生长 + 环境自适应

$$
P_{n+1}, V_{n+1} = \mathcal{T}(P_n, V_n, E_n)
$$

其中：
- $P$：规划器（相对稳定，靠 Loom / HTN 演进）。
- $V$：**归约器集合**（可变，是 L2 的主角）。
- $E_n$：外部环境反馈（执行结果、用户反馈、真实世界信号）。

L2 的核心机制：

1. **反馈采集**：规划结果 + 执行结果 + 最终成品 + 用户反馈 → OpenTelemetry 全量可回溯。
2. **归约器生成管道**：
   - 输入：历史失败案例（DAG + 反馈）。
   - LLM 在独立上下文中生成一个新的归约器（代码 + 逻辑规则），它能拦住这类问题。
   - 沙箱编译校验 + 在若干历史案例上回测 → 通过才被采纳。
3. **归约器的选择与组合**（HTN 层）：
   - 给定一个新项目，Prolog 推理引擎根据项目分类、归约器之间的逻辑关系，输出本项目启用哪些归约器、以什么顺序调用。
   - 这是**维度的演算**（合一 + 回溯 + 谓词折叠），不是简单的"全部启用"。
4. **归约器的迭代**（暂缓）：
   - 每个归约器跑完后打分，通过率低时触发"归约器本身的改进"——这是"归约器的归约器"（套娃），可能暂不实现。

L2 能做到什么：

- 拦住的低质量问题种类**单调增长**——每个被暴露的错误都物化为一条永久归约约束。
- 归约器之间的组合由 Prolog 推理而非硬编码，能适应新项目类型。
- 在环境稳定时收敛到当前归约器集合约束的极限。

L2 做不到什么：

- **不能主动改造环境**。L2 被动响应环境反馈（执行结果、用户反馈），但不主动改变环境使其更适合自身。
- **不能跳出自身逻辑框架**。归约器只能在已有的逻辑维度上增加约束，不能创造新维度。
- **容易陷入局部最优**。归约器一旦被采纳，倾向于在历史失败案例上过拟合，对未来未见过的问题可能过度严格。

一个类比：L2 像一个**不断扩充质检工序的工厂**——每发现一种新问题就加一条质检线，质检线越来越多、越来越细，但质检本身的"标准"是固定的（"什么是合格"由 LLM + 反馈决定，不由工厂主动改造）。质检线太多时，工厂会在"拦得太死"和"放过新问题"之间拉扯。

## 四、L2 的射程：哪些工作在内、哪些在外

这是使用者最该关心的边界。用一句话切分：

**在射程内——"又长又难，但人类已知怎么做"的工程类任务。** 写小说、剪视频、按需求出代码、做数据流水线……这类任务的共同点是：人类反复做成过，"好办法存在"是有保证的（[[逻辑向 AI|Logic-Oriented-AI]] 第四节的构造性保证）。L2 的归约器生长机制 + 外部反馈，理论上能覆盖的就是这一片——质量约束逐步收紧、反馈逐步闭环。

**在射程外——范式创新。** 这里说的"范式创新"，指计算机科学语境下的认知框架突破。例如：图灵提出可计算性模型、冯诺依曼定义现代计算机体系结构...

它落在射程外有两个叠加的原因：

1. **符号接地失效**：新范式要创造的是**训练分布外的新概念**，而 LLM 的接地依据是语料共现——新范式在语料里没有共现支撑（[[逻辑向 AI|Logic-Oriented-AI]] 第三节明说的失效区）。
2. **搜索无从下手**：搜索空间是"所有可能的新框架"，NP-hard 起步，且**没有好的启发式起点**——LLM 在这里给不出比随机更好的方向。

所以"LLM + 逻辑能否胜任范式创新"是一个**缺乏乐观理由的开放问题**：不是被证明不可行（存在性有保证，人类做到过），而是**没有任何理由相信当前方法能廉价找到**。本路线因此明确**不承诺、也不以范式创新为目标**。

一个必要的区分：**范式创新** 与 **范式确立后的工程化** 是两回事。图灵提出计算模型是前者（射程外）；把图灵模型用于设计具体编译器是后者（射程内，已知怎么做）。绝大多数人类工作属于后者——这也是本路线仍然值得做的原因。

## 五、L2 → L3 的未知地带

L2 已知的天花板是**陷入局部最优**——归约器集合在历史反馈上过拟合，对未来未见过的问题可能过度严格或不足；同时 L2 不能主动改造环境。

Unigen 现阶段不解决 L3 —— L3 属于认知模型 / 世界约束层（见 [[prism]] 第九节）。

---

## 六、Unigen 的工程决策

1. **聚焦 L2，不承诺 L3**。W1~W6（见 [[路线图|Roadmap]]）的目标是 L2 的归约器动态生长，不是"造神"。形式化中的 $V^*$ 是**当前框架下够用的归约器集合**，不是终极答案。
2. **外部环境反馈是刚需**，不是可选项。没有 $E_n$，归约器生成管道没有输入数据，系统退化为 L1。
3. **接受局部最优**。L2 没有逃出局部最优的内禀机制。对策是：多样化基准案例集、人工介入打破僵局、坦然接受"在当前归约器集合下已是最好"。
4. **HTN / Prolog 的定位**。HTN 是**规划器的完整表达**——任务分解（compound task → subtasks，递归 method 展开）+ 归约器组合（哪些约束在本项目启用）+ 时序事实链（状态演化）。当前 Loom 是 HTN 的退化版本（无前置/效果模型、无时序事实链、归约器硬编码）。`designDag`（`p1-design.ts`、`dag.ts`）和 `logicalExpand`（`p2-expand.ts`）已经在做任务分解，只是没有用 Horn 子句形式化——它们是 Loom 而非 HTN。HTN 化的目标是**让这层逻辑可被 Prolog 推理统一调度**，而非"另起一个独立的子系统"。明确这一点可以避免把 HTN 与规划器割裂看待。
5. 只实现L2（"在给定逻辑框架与归约器集合下持续适应、收敛到极限"），不暗示 L3。这已极有价值，但它不是无限的。

## 七、约束器与人类概念的同构性

L2 架构中生长出的**归约器集合**，与认知科学对"人类概念"的某种主流解释存在结构同构。这一点值得说明，因为它揭示了本路线长期演化的一个深层特征——但不应当作"已实现"或"已证明"来宣称。

**认知语言学的框架**（Lakoff 等）：人类的概念不是字典里严格的充要条件定义，而是**"原型 + 约束集合"**。例如"椅子"这个概念在你脑中的表征不是某条充要条件，而是若干约束的组合（能承重、有可坐平面、高度约 40-60cm……）。当你看到一个怪设计，你的"约束网"瞬间裁决"是/不是椅子"。

**Unigen 的归约器集合**与这一图景**结构同构**：归约器 = 单条约束；归约器的组合 = 概念；从反馈中生长归约器 = 概念的形成（"吃一堑长一智"）。两者的核心机制都是：
1. 由若干约束组成的网络。
2. 约束随经验沉淀 / 提炼 / 合并。
3. 用约束网络对候选实例做"类属成员"判断。

**但需注意**：
- 这是**结构同构**，不是**实现等价**。人类概念还有时间、情境、具身、隐喻等维度（Lakoff 自己强调 embodiment），Unigen 的归约器不涉及这些——它建模的是"概念"的某个抽象骨架，不是完整概念。
- "同构"也不意味着"路线终将造出人类智能"。Unigen 仍是一个**特定垂直领域的工程工具**，它的演化有清晰的工程边界（见上文 L2/L3 切分）。同构不等于智能。
- 因此，这一观察的价值在于**揭示 L2 路线的演化方向与人类概念形成机制方向一致**，而非"实现认知"。
